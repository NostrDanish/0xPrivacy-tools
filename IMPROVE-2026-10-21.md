# Improvement Deep-Dive — NostrDanish/0xPrivacy-tools — 2026-10-21

Dependency-free static PWA (plain HTML/JS tools + vendored crypto). Files inspected: sw.js, index.html, tools/ listing, tools/nostr/index.html, assets/js/lib/ + assets/js/lib/noble/ listings, noble/sha256.js header, README.md, LICENSE (MIT).

## Top recommendations (ranked, with effort S/M/L)

1. **Version and integrity-pin the vendored crypto (S–M)** — `assets/js/lib/noble/*` (sha256, blake2s, blake3, utils…) is a hand-copied snapshot of @noble/hashes with NO version comment, no LICENSE header, no integrity record. The vendored API shape (`import { HashMD } from './_md.js'`, separate `sha256.js`/`blake2s.js` modules) matches the @noble/hashes 1.x line; upstream is at 2.4.0 (Aug 2026, ESM-only, module renames: sha256→sha2, blake2s→blake2, plus a March-2026 self-audit and a blake3 tree-merging correctness fix in 2.4.0). For a privacy-tools site whose entire value proposition is "verify locally", unverifiable crypto provenance is the core weakness. Fix: add `assets/js/lib/VENDORED.md` recording package@version, upstream URL, date, and SHA-256 of each file; better, re-vendor from @noble/hashes 2.4.0 with the new module layout and add a tiny update script.
2. **Service-worker cache hygiene (S)** — `sw.js` uses a hardcoded `CACHE = '0xp-v1'` with cache-first for everything including `index.html`: after a deploy, returning users keep the old shell until someone manually bumps the string. Fix: derive the cache name from a build stamp (e.g. `0xp-<deploy-sha>` injected at publish), and use network-first (or stale-while-revalidate with revalidate-on-navigation) for `index.html`/tool HTML while keeping cache-first for the versioned vendored libs (they become immutable once content-addressed by VENDORED.md).
3. **Add a minimal CI gate (S)** — no `.github/` at all: no test, no lint, no syntax check. A broken `sw.js` or HTML edit goes straight to Pages. Add one workflow: parse-check each `assets/js/**/*.js` (`node --check`), validate `manifest.webmanifest` JSON, and verify every path in the SW `SHELL` list exists (a 404 in `addAll` rejects install — currently unchecked).
4. **SW precache correctness test (S)** — `SHELL` lists 16 files by hand; there is no check that `assets/js/lib/hashes.js` etc. still exist after a refactor. Cheap node script in CI (see #3) or generate the list at build time.

## Missing gates (CI/tests/protection)

- No CI of any kind (no `.github/workflows`, no `.gitlab-ci.yml`).
- No tests: `bech32.js` encodes/decodes nsecs — a silent corruption bug here is worst-case; add a 20-line known-answer test page or node test run in CI.
- No branch protection on main; repo is public — enable secret scanning + Dependabot (no deps, but scanning still matters for a site that invites users to paste key material into client-side decoders).

## Quick wins (code/config)

- `sw.js` fetch handler caches any 200 `basic`/`cors` GET — including third-party CORS responses, which then pin cross-origin content into the offline cache indefinitely; restrict runtime caching to same-origin.
- `sw.js` never bumps `CACHE` — combine with a `self.skipWaiting()`-triggered `postMessage` "update available" toast in shell.js.
- `tools/nostr/index.html` kindName table maps 1063 to "HTTP auth (NIP-98)" (should be "file metadata"; NIP-98 is kind 27235) and omits 30078/24133 — small accuracy pass.
- The nsec↔hex decoder is client-side only (verified: no network calls, no storage) — keep it that way and say so explicitly next to the input ("never leaves this page; for real keys prefer a signer").
